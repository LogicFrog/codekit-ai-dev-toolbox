## 详细分工

### A（组长）

分工覆盖项目最核心的三条主线：**数据库全局设计**、**向量化方案**、**AI Agent 决策链路**。这三块是系统的骨架和大脑。

**数据库概念设计（模块3）**：梳理系统全部实体——代码片段、分类、依赖关系、版本快照、向量嵌入、搜索历史共六个核心实体，定义每个实体的属性集合和主键，分析实体间的 1:1、1:N、N:M 关联（代码片段与分类的多对一、片段与标签的多对多、片段与版本快照的一对多、片段与向量嵌入的一对一），绘制全局 E-R 图并撰写设计说明，解释为何将嵌入向量独立成表而非内嵌在片段表中、为何用 `code_snippet_tags` 中间表而非逗号分隔存储标签。

**数据库逻辑设计 + 向量化方案（模块4）**：将全部 E-R 概念转换为 7 张标准关系表，标注主键、外键、唯一约束、非空约束，分析表结构是否满足第三范式，说明实体完整性（主键 AUTO_INCREMENT）、参照完整性（`ON DELETE CASCADE/SET NULL` 策略选择理由）、域完整性（`VARCHAR` 长度限定、`INT` 默认值）的具体实现。重点是向量化方案的数据库设计：为什么选择 `LONGTEXT` 存储 JSON 数组而非 MySQL 原生 VECTOR 类型（保持 H2/MySQL 双数据库兼容）、`embedding_dim` 字段的设计意图（支持不同模型切换）、为什么在应用层计算余弦相似度而非在 SQL 中做向量运算（批量加载 5000 条嵌入后在 Java 内存中比对的性能优势）。

**AI Agent 决策链路（模块5核心部分）**：描述 Agent 如何接收自然语言指令后完成"理解→规划→调度→执行"的全链路——LLM 规划器根据提示词模板将用户意图拆解为有序子任务列表（如"帮我找到令牌代码并解释优化"→拆为 `code_search` → `code_optimize`），Skill 注册中心根据任务名匹配执行器，编排器串行调度各 Skill 并通过上下文 Map 传递中间结果，最终合并输出。同时说明核心优化决策：将 `ai_explain` + `code_optimize` 两次独立的 LLM 调用合并为一次 `explain_and_optimize` 调用，减少约 50% 的 API 耗时，使 Agent 三任务场景能够在客户端超时窗口内完成。

**统稿审核**：最终通读全报告，统一术语、格式和写作风格，标注各模块间的交叉引用，准备答辩 PPT 和讲解逻辑。

### B — 功能需求分析

负责**模块2：功能需求分析**的完整撰写。围绕"智能代码资产管理系统"定位，梳理三类使用者场景：开发者日常通过关键词或自然语言搜索查阅代码片段，项目管理员批量导入本地代码库并进行分类与标签管理，AI Agent 自动执行代码解释、优化建议、版本对比等任务。按照四方面展开撰写——业务场景描述（代码文件监听、代码解析入库、搜索查阅、版本追踪、AI 辅助分析的端到端流程）；功能需求整理（本地代码目录自动监听与增量导入、关键词+语义双模搜索、代码片段分类与标签管理、历史版本快照与回滚、AI 解释与优化建议生成、Agent 任务编排执行）；数据需求分析（每项功能需要哪些表的哪些字段支撑，如搜索功能依赖 `code_snippet` 的 FULLTEXT 索引和 `code_embedding` 的向量数据）；非功能需求（全文检索响应时间不超过 2 秒、语义检索最低相似度阈值 0.7、文件监听间隔 5 秒可配置、支持 MySQL 和 H2 双数据库切换、搜索关键词缓存至 Redis 加速热点查询）。

### C — 课程设计说明 + 文件管理与版本模块

负责**模块1：课程设计说明**的全文撰写。说明设计题目为"智能代码资产管理系统——基于 MySQL 的代码库全生命周期管理平台"。阐述设计任务：构建一套支持代码文件扫描导入、全文与语义双模检索、版本历史追踪、AI 辅助代码分析的数据库应用系统。列出整体实验要求：基于 MySQL 关系型数据库，采用 Spring Boot + JPA/Hibernate 持久层框架，遵循需求分析→概念设计→逻辑设计→物理设计→实施的完整流程，设计至少 6 张业务表并完善实体/参照/域三类完整性约束。最后描述运行环境：JDK 21、Spring Boot 4.0.3、MySQL 8.0+（InnoDB 引擎）、Redis 7.0（可选缓存层）、H2 嵌入式数据库（桌面版备用）、Apache Maven 构建管理、跨平台支持（macOS/Windows/Linux）。

同时负责**模块5中的代码文件管理部分**：描述 Apache Commons IO 文件监听器如何以 5 秒轮询间隔扫描指定目录下的 Java/Python/JavaScript 等源文件变更事件；Java 代码解析器如何通过 AST 提取包名、类名、方法签名、import 依赖关系并自动打标签（如检测到 `@RestController` 注解自动标记为 Controller 分类）；MD5 哈希算法如何实现增量扫描去重——同一文件内容不变则跳过解析、内容变化则更新 `code_content` 与 `file_md5`、文件移动则更新 `file_path` 保持 `file_md5` 不变；以及 `code_category` 表的分类体系（Controller、Service、Repository、Entity、Config、Util 等）的设计依据。

负责**模块5中的版本管理部分**：描述 `version_info` 表的结构设计思路——以 `snippet_id` 为外键关联代码片段，每次检测到文件变更时自动创建版本快照（存储完整代码内容、版本标签、变更描述）；JGit 库的 Histogram 差异对比算法如何在两个版本之间生成行级 diff；版本回滚功能如何从 `version_info` 中读取历史快照覆盖当前文件；AI 版本分析如何将两个版本的差异统计和代码内容发送给 LLM，获得风险评估、测试关注点和改动摘要。

### D — 源程序代码（DDL + 测试数据 + 截图）

负责**模块6的上半部分**。编写完整的建库建表 DDL 脚本，从 `CREATE DATABASE codekit` 开始，依次创建 7 张表的 `CREATE TABLE` 语句，每行附带注释说明字段含义和约束意图——包括主键 `AUTO_INCREMENT` 声明、外键 `REFERENCES table(column) ON DELETE CASCADE/SET NULL` 约束、唯一索引 `UNIQUE KEY uk_file_path(file_path)` 和 `UNIQUE KEY uk_category_name(category_name)`、全文索引 `FULLTEXT INDEX ft_combined(file_name, class_name, code_content) WITH PARSER ngram`、CHECK 约束 `CONSTRAINT chk_search_type CHECK (search_type IN (0, 1))`、字段默认值（`sort_order INT DEFAULT 0`、`search_type INT DEFAULT 0`）。然后编写 INSERT 测试数据脚本——`code_category` 表插入 Controller、Service、Repository、Entity、Config、Util、DTO 七条分类数据；`code_snippet` 表插入 8 条以上不同语言、不同包路径的真实代码片段（附完整代码内容）；`code_snippet_tags` 为每条片段关联 2-3 个语义标签；`version_info` 为其中 2 条片段各创建 2-3 个版本快照，体现迭代修改过程；`code_embedding` 插入对应的向量嵌入 JSON 数据（可使用简化的模拟向量）。最后整理关键界面运行截图——代码搜索页面（展示关键词输入与结果列表）、分类浏览页面（展示按分类筛选的片段列表）、版本对比页面（展示两个版本的 diff 高亮视图）、AI 解释结果页面（展示 Agent 返回的解释与优化建议）——并标注每张图在报告中的编号位置。

### E — 源程序代码（查询+高级特性） + 实验总结

负责**模块6的下半部分**。编写 8-10 条代表性业务查询 SQL，每条附注释说明用途和预期结果：按类名关键词模糊搜索（`WHERE class_name LIKE '%Token%'`）；MySQL 全文检索（`SELECT * FROM code_snippet WHERE MATCH(file_name, class_name, code_content) AGAINST('token' IN NATURAL LANGUAGE MODE)`）；按分类统计代码片段数量（`SELECT c.category_name, COUNT(s.id) FROM code_category c LEFT JOIN code_snippet s ON c.id = s.category_id GROUP BY c.id`）；查询指定片段的所有标签（`SELECT tag_name FROM code_snippet_tags WHERE snippet_id = ?`）；查询指定片段的所有历史版本（`SELECT version_name, create_time FROM version_info WHERE snippet_id = ? ORDER BY create_time DESC`）；搜索热词排行（`SELECT keyword, COUNT(*) AS cnt FROM search_history GROUP BY keyword ORDER BY cnt DESC LIMIT 10`）；跨表关联查询（片段+分类+标签三表 JOIN 的完整信息查询）；分页查询（`LIMIT ? OFFSET ?`）。同时设计一个视图 `v_hot_keywords` 封装热词排行聚合逻辑；一个存储过程 `sp_batch_update_md5` 实现批量重新计算所有代码片段的 MD5 哈希值（使用游标遍历 `code_snippet` 表，调用 `MD5()` 函数更新 `file_md5` 字段）；一个触发器 `trg_update_time` 在 `code_snippet` 表执行 UPDATE 操作前自动将 `update_time` 刷新为当前时间戳。所有 SQL 代码附带执行结果的截图证明其可正常执行。

负责**模块7：实验总结**的完整撰写。记录从数据库需求分析到概念设计、逻辑设计、物理设计、编码实施的全流程操作步骤；整理开发中遇到的关键问题及解决过程——MySQL 的 FULLTEXT 全文索引默认不支持中文分词导致搜索结果为空，排查后改用 `WITH PARSER ngram` 重建索引才正常生效；H2 嵌入式数据库不支持 MySQL 专有的 `MATCH AGAINST` 语法，在 JPQL 查询中使用 `LIKE` 模糊匹配降级替代以保证双数据库兼容；语义搜索首次加载 5000 条嵌入向量耗时接近 3 秒影响体验，通过 `idx_update_time` 索引实现增量分页加载将首次加载时间降至毫秒级；Agent 编排三个 Skill 串行调用 LLM 时总耗时约 160 秒超过客户端 120 秒超时，通过合并 explain + optimize 为一次 LLM 调用将总耗时压缩至 80-100 秒解决。最后撰写学习心得——对数据库设计规范化的理解（3NF 范式实践体会、何时适度反范式、索引选型策略对查询性能的实际影响）；JPA/Hibernate 框架使用经验（`@ElementCollection` 实现 N:M 标签关联的便捷性、`ddl-auto: update` 自动建表的便利与风险、JPQL 与原生 SQL 的取舍）；以及"数据库设计必须植根于需求分析，任何脱离业务的表结构设计都是空中楼阁"的核心认识。
